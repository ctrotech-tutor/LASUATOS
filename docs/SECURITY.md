# Security and privacy

## Current security state

LASUATOS runs in production for a pilot with real LASU students. Students open accounts from class lists uploaded by their HOC or an administrator, confirming a code sent to their LASU student email (or Google); staff join only by invitation. Every route derives the caller's role and area from the server session (ADR 004). Public free-form sign-up is off by default (`STUDENT_SIGN_UP=class_list`) and can never choose a role.

A confirmed email proves control of a mailbox, not LASU student status; matric numbers come from the class list and are checked for shape, not against LASU's records. Lecture attendance is marked with the student's own account and checks a 30-second QR code, the student's face, the phone rule and, for mapped venues, the phone's position (`docs/VERIFICATION.md`). None of these is proof of presence or identity on its own. The guarded local seed includes only synthetic demo data under a clearly labelled tenant; it never seeds official University records.

Passwords are hashed with Node.js scrypt using a per-password random salt. Email verification, password reset, invitation and session tokens are generated from 256 bits of randomness and stored only as SHA-256 digests. Verification and reset links expire after 30 minutes and are single-use. Session cookies are HttpOnly, SameSite=Lax, Secure in production, and expire after 30 days. Account owners can list their sessions, sign out one or all other sessions, change their password and recover a forgotten password (see "Account protection" below). The PostgreSQL adapters are exercised against PGlite (embedded PostgreSQL) in integration tests, and the sign-in, check-in and face paths against a local PostgreSQL 16 in the load tests.

Rate limiting, cross-origin request checks and security headers are implemented in the API, and the web app sends its own security headers (below). They reduce, but do not remove, abuse risk: there is no bot challenge, and Vercel's edge adds only the platform's own protection. Email alerts (ADR 020, ADR 029) cover server errors, page crashes, an out-of-date schema, bursts of server errors, of `429` refusals and of wrong-password sign-ins, failing email providers and Google sign-in, failed or late backups, bursts of cross-origin `403` blocks and a failing rate-limit store (ADR 036). A deep security review in November 2026 is summarised below (ADR 033); it is not an independent audit.

The API redacts email, name, matric number, password, token, code, location and cookie fields in request logs, as well as dispute statements and decision notes. For local development, `compose.yaml` provides loopback-only PostgreSQL and Mailpit; Mailpit captures mail without contacting real inboxes.

Device location is collected only at check-in for sessions linked to a mapped venue, as proximity evidence. There is no compliance certification or institutional approval claimed.

## Account protection (Phase 10)

**Rate limiting.** One policy table (`apps/api/src/security/rate-limit-policies.ts`) applies fixed-window limits before route handlers run:
- **Keys:** client address, normalized email, matric number, session, and the account a classmate signs in with at a lecture check-in. Signed-in actions (enrollment, course check-in, disputes, administration) use the session, because a whole lecture can share one campus NAT address. The full table is in `docs/API.md` (*Rate limits*), generated from the policy file and checked by a test.
- **QR attendance** (`/api/v1/lecture/resolve` and `/check-in`, no account needed) is limited per address at 20,000 requests per 10 minutes, with typed-code misses limited to 600 per 10 minutes per address so codes cannot be guessed. Nothing is keyed on the QR ticket: everyone who scans in the same second shares one ticket, and such a limit refused most of a full hall in the crowd test (`docs/LOAD_TESTING.md`). A phone can mark its owner and one classmate per session (the phone rule, ADR 033), and two students on one phone are flagged to the session taker. Signing in a classmate on the check-in page is limited to 600 per address and 10 per account per 15 minutes.
- **Counting:** every attempt counts, successful or not, and all of a request's rules are counted so tripping one cannot hide the others. A blocked request gets `429` with `Retry-After` and a plain-language message.
- **Storage:** counters live in PostgreSQL (`rate_limit_counters`), shared by every API instance. The row key is a SHA-256 digest of the policy and subject, so raw addresses, emails and tokens are never stored. Expired windows reset on the next hit and are pruned opportunistically.
- **Failure mode:** if the counter store fails, requests are allowed and the failure is logged (fail-open), so a database hiccup cannot lock everyone out of sign-in or check-in. Five failures within 5 minutes email the operator (`rate_limit_store`), counted in memory because the shared store is what is failing. Production refuses `RATE_LIMIT_STORE=off`.
- **Coverage:** every route that changes something has a limit, except sign-out. `rate-limit-coverage.test.ts` lists every registered `POST`, `PUT`, `PATCH` and `DELETE` route and fails if one has neither a limit nor a written reason (ADR 036).
- **Client addresses** come from `X-Forwarded-For` only when the immediate peer matches `TRUST_PROXY` (default `loopback`, which fits the Next.js rewrite on the same host). A wrong `TRUST_PROXY` either merges everyone into one address or lets clients choose their own; set it to the load balancer's addresses in production.
- **Embedded mode (free Vercel setup, ADR 015)** does not read `X-Forwarded-For` or `TRUST_PROXY`. The client address is Vercel's `x-real-ip`, which the platform sets itself. Use embedded mode only on a host whose edge overwrites that header.
- **The limits are starting values** for the pilot, to be tuned from observed traffic. They are not a capacity statement.

**No hard lockout.** Repeated sign-ins are throttled (10 attempts per email and 600 per address per 15 minutes; the address limit is sized for a lecture hall behind one campus address) rather than locking the account. A lockout would let anyone who knows a student's email block that student from signing in before a lecture. Throttling makes guessing impractical without giving others that power.

**Password recovery.**
- **Request** (`POST /api/v1/auth/password-reset/request`): the response is the same `202` whether or not the address has an account, is unverified, is suspended or is in the two-minute cooldown, so it cannot be used to discover accounts. Only active, email-verified accounts with a password receive a link. A pending student must use the confirmation link instead, so recovery cannot bypass email confirmation.
- **Token:** one token per user (a new request replaces the old one), stored as a digest. It expires in 30 minutes and is single use. The link carries the token in the URL fragment, which browsers do not send to servers; the reset page removes it from the address bar and history. The page sends `no-referrer` and `no-store`.
- **Completion** (`POST /api/v1/auth/password-reset/complete`): one transaction consumes the token, replaces the password hash and revokes **every** session of the account. The browser's cookie is cleared and the owner is emailed a notice.
- **Change** (`POST /api/v1/auth/password`): requires the current password. It revokes every other session and invalidates any pending reset link. The owner is emailed a notice. Notices are best effort: a delivery failure is logged, but the change still stands.

**Sessions.** `GET /api/v1/auth/sessions` lists the caller's live sessions with created, last-active and expiry times and marks the current one; tokens are never returned. Last-active is refreshed at most once every 5 minutes per session to limit writes. `DELETE /api/v1/auth/sessions/:id` signs out one other session and `POST /api/v1/auth/sessions/revoke-others` signs out all others. Both are limited to the caller's own sessions (`404` otherwise); the current session ends through normal sign-out. Device names, IP addresses and user agents are deliberately not recorded.

**Cross-site request forgery.** In addition to `SameSite=Lax` cookies, every state-changing API request (`POST`/`PUT`/`PATCH`/`DELETE`) passes an origin check (`apps/api/src/security/origin-guard.ts`):
- `Sec-Fetch-Site: cross-site` is rejected.
- `same-origin` and `none` are accepted.
- Otherwise the `Origin` must exactly match `PUBLIC_APP_URL` or an entry in `TRUSTED_ORIGINS`. `Origin: null` is rejected.
- Requests with neither header come from non-browser clients, which carry no ambient browser cookies to forge, so they are accepted.

A blocked request gets `403` with an explanation. There is no separate CSRF token. Twenty blocks within 10 minutes email the operator (`origin_blocked`), with the last route, the origin (scheme, host and port only) and the `Sec-Fetch-Site` value. A burst usually means a new address is serving the app and is missing from `PUBLIC_APP_URL` or `TRUSTED_ORIGINS`, or that the guard is stopping an attack.

**Security headers.**
- **API:** every response gets `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, a restrictive `Permissions-Policy` and same-origin resource and opener policies, plus HSTS in production.
- **Web pages** (`apps/web/next.config.ts`): a CSP that allows only the app's own scripts, styles and API, data-URL QR images and OpenStreetMap tiles; `frame-ancestors 'none'`; `X-Frame-Options: DENY`; `nosniff`; `strict-origin-when-cross-origin` referrers (OpenStreetMap's tile policy needs a referrer); and a `Permissions-Policy` that allows geolocation only on this origin, for venue check-in. HSTS and `upgrade-insecure-requests` are sent when `PUBLIC_APP_URL` is HTTPS.
- **Known gap:** the page CSP still permits inline scripts, because the Next.js App Router emits inline bootstrap scripts. A nonce-based CSP (middleware plus dynamic rendering) is the follow-up. Until then the CSP limits where content can load from and blocks framing, but it is not a full defence against injected inline script.

**Error alerts.** Alert emails (`apps/api/src/monitoring/alerts.ts`) carry the route pattern (for example `GET /api/v1/lecture/sessions/:sessionId`, so no IDs or query strings), the error type and message, and the request ID. Request bodies are never included. The error message is shortened, and text that looks like a connection string, an API key or a `token=`/`password=`/`cookie=` value is replaced with `[hidden]` before sending. Browser crash reports (`POST /api/v1/client-errors`) are origin checked and rate limited, always answer `204`, and are only ever turned into an email to the operator, so they cannot be used to reach anyone else. They get at most 5 of the 20 alert emails a day, checked first, so made-up reports cannot crowd out server alerts.

**Logging.** One shared redaction list (`apps/api/src/security/headers.ts`) is used by both the default and production loggers. It covers cookies, `Set-Cookie`, authorization, email, names, matric numbers, all password fields (`password`, `currentPassword`, `newPassword`), tokens, codes, locations, dispute statements and notes.

## Staff provisioning (Phase 11)

- **No self-service staff roles.** Public sign-up creates students only. Lecturers and administrators exist only through invitations: the first from the server-side `pnpm admin:bootstrap` command, the rest from an administrator's Staff page. Email domain never grants a role.
- **Scope.** Administrators may invite and manage people at or below their own level, inside their own area. This is decided on the server from the session's role assignment; browser-supplied faculty and department ids are only checked against it. Out-of-scope and unknown ids get the same response. System-administrator roles cannot be invited, and nobody can suspend or reactivate themselves.
- **Invitation tokens.** 256 bits from a CSPRNG, stored only as a SHA-256 digest, valid for 7 days and single use. Resending replaces the digest, so older links stop working. Links carry the token in the URL fragment; `/accept-invitation` strips it from history and is served with `no-store` and `no-referrer`. The admin API never returns the token. The bootstrap command prints it only when no email could be sent or `--print-link` is given.
- **Acceptance** creates the account, confirms the email, creates the profile and scoped role assignment, and consumes the invitation in one transaction with the invitation row locked, so a link cannot be accepted twice. It re-checks that the email is still unused, the staff number is free, and the faculty or department is still active.
- **Suspension** revokes every session of the account in the same transaction. Session lookup and sign-in require an active account, so the person is signed out on their next request.
- **Audit.** Every invitation, resend, revoke, acceptance, suspension and reactivation is written to `staff_audit_events` (actor, target, reason, time). A trigger rejects updates and deletes.
- **Rate limits** (pilot starting values): invite and resend 30 per hour per session; preview 30 and accept 20 per 15 minutes per address. Invitation emails are logged on failure without the token.
- **Limits.** The product does not verify that an invitee is really LASU staff; the inviting administrator vouches for that, and the audit trail records who did.

## Student accounts and face verification

- **Opening an account** needs a matric number on an uploaded class list and the 6-digit code sent to the LASU student email (on the list, or typed by the student when the list has none; it must end in `@st.lasu.edu.ng` and be unused). Lookups, code requests and opening are rate-limited per address and per matric number; the lookup shows the full class-list name, department and level (so students recognise themselves) but never whether an account still uses its starting password. The address a code was sent to is shown in full when it is a LASU address (it follows the listed name, and students need it to know which mailbox to open). A personal address (students on a JAMB number) is shown only partly, `ku•••@gmail.com`, here and in every message a stranger can trigger (ADR 033). Opening the account still needs the code sent to the LASU email, so knowing someone's matric number and name is not enough.
- **Starting password** `LASU<matric><SURNAME>` follows the LASU portal convention the students already know (a Direct Entry student who opens with a JAMB number gets `LASU<JAMB number><SURNAME>`; it stays when they switch to their matric number, and a password reset refuses the starting password built from either number). It is guessable by anyone who knows the student, so it is not the protection: opening needs the email code, and every check-in needs the student's face. The account is flagged (`password_is_default`) and the student is asked to change it. It is stored as an scrypt hash like any password.
- **A session started with the starting password proves nothing** (ADR 033). Sign-in marks it (`user_sessions.starting_password`), and the mark counts while the account is still on that password. A marked session cannot register a face, cannot change the password with the current one (the new one needs the emailed code or Google, which starts a fresh session and signs out every other), and cannot mark attendance while face checks are off. Sessions from opening the account, a reset, a setup code or Google are never marked.
- **Face check at attendance** (`FACE_CHECK=required`), for lecture **and** course check-ins (ADR 033): the face must match the registered face, the head must turn the way the scan asks, and passive liveness must pass. Six failed tries per class per 30 minutes block further tries and are audited. A phone marks at most two students per class, counted again under the session lock. A course check-in is two calls: the code or QR earns a 10-minute ticket signed for that student, and only the ticket plus matching photos writes the record (with its `face_score`). Passive liveness is not certified presentation-attack detection; the venue check, shared-device flag and the session taker's list stay in place.
- **Duplicates:** a face too close to another student's registered face is refused and audited, so one person cannot hold two accounts.
- **Recovery without a takeover hole.** The proof of who owns a student account is a confirmed LASU email. An account without one (opened the old way, or by someone else with the student's matric number) is taken over by the listed student who confirms the LASU email or brings a HOC setup code: new email, starting password, all sessions and reset links revoked, face deleted, attendance kept, and the old address told. An account *with* a confirmed LASU email can never be taken over by a code: its owner resets the password with a code to that email (or the reset link, by email or matric number). Only an administrator can **release** it (wrong email on the list, wrong person got in), with a reason that is audited; the corrected email goes on the list so only the real student can open it again, and the previous address is told.
- **Setup codes** are 8 characters from a CSPRNG (about 40 bits), stored as a SHA-256 digest, single use, 30 minutes, five tries, rate-limited, and shown once to the HOC. They are refused for confirmed accounts. Opening with one leaves the email unconfirmed but *vouched*: matric number and list name are locked and the face can be registered, and a later email-code takeover still wins (and removes the face).
- **Continue with Google** (ADR 027, only when `GOOGLE_CLIENT_ID` is set) can stand in for any emailed code. Scope `openid email` only: no access to the mailbox, and no client secret to leak. The ID token's RS256 signature is checked against Google's published keys, with the issuer, audience, expiry, an age of at most 15 minutes, `email_verified`, and a nonce tied to both this browser (only its SHA-256 digest goes to Google) and the step it was made for. LASU addresses also need Google's `hd = st.lasu.edu.ng` claim. The confirmed address then has to pass the same checks as a code address, and new face photos still need the password. Tokens are never stored or logged; refusals log only the reason. The return page removes the token from the address bar and history straight away.
- **LASU mail** (ADR 030, only when `LASU_MAIL` is on) is browser-only: a one-hour `gmail.readonly` access token kept in that tab's `sessionStorage`, used only against `gmail.googleapis.com`, never sent to or stored by our servers; no refresh token exists. The page checks the mailbox is in `LASU_MAIL_DOMAINS` and revokes anything else. Email HTML is cleaned and shown in a sandboxed `srcdoc` frame without scripts; remote pictures load only on request, without a referrer. Sign-out forgets the token; Disconnect also revokes it at Google.
- **Sign in with Google** (ADR 028) opens a session only for an active account whose email is already confirmed and is the exact address Google vouches for (LASU addresses with `hd = st.lasu.edu.ng`; otherwise only Gmail or a Workspace domain's own address). An unconfirmed student account is never handed over this way, so an address typed during a setup-code opening cannot be used to get in. The proof's purpose is `signin`, so a proof made to open an account or reset a password cannot sign in, and vice versa.
- **Names** of students confirmed by the list cannot be changed by the student (the HOC corrects the list); other accounts need a first name and surname, without initials.
- **Password change is prompted, never forced.** A student on the starting password sees a reminder (home card and setup screen); signing in is not blocked. Only a session started with the starting password is held back, and only from registering a face and changing the password without a code.
- **New face photos** need the password and a code sent to the LASU email, open a 20-minute window, must still match the registered face, and are limited to 2 per 30 days. A thief with an unlocked phone cannot swap in their own face.
- **Help requests** (manual add after two failed face checks) need the student's own signed-in account and a fresh scan ticket; the person taking attendance decides while looking at the room, with the registered photo. Class-rep limits (open session, inside the venue, 10 per lecture) apply.
- **Face reviews** are for lecturers and administrators only; class reps cannot reject a classmate's check-in. Rejecting needs a reason and removes the check-in; every decision is audited.
- **Audit log** is read-only and scope-filtered; faculty and department administrators do not see other areas' student events.
- **Retention:** face data is deleted a grace period after a set graduates (unless the student still checks in), check-in photos after 90 days. The cron route compares `CRON_SECRET` in constant time and refuses requests without it.
- **Sign-ins and codes:** sign-ins that ended more than a day ago are deleted nightly (each person's latest is kept for "last active"), as are spent or expired email codes, setup codes and reset or confirmation links (ADR 032).
- **Logs and alerts:** request log lines hold the method, the path without its query string and the host; no IP address, port or user agent. Alert text is scrubbed of email addresses and crash reports name only a coarse browser and system.

## Security review, November 2026 (ADR 033)

A deep review exercised all 182 API routes as every kind of account and signed out, sent 27,630 fuzzed requests, and audited dependencies. Nothing leaked across areas or roles, and production dependencies have no known advisories (one dev-only advisory, in a build tool's glob matcher). Fixed:

| | Finding | Fix |
| --- | --- | --- |
| High | The starting password could register someone else's face or change their password | Starting-password sessions are marked and limited |
| High | Course check-ins skipped the face check and the phone rule | Two-step check-in: ticket, then face; two students per phone |
| High | The room check was off unless switched on | On by default for mapped venues |
| Medium | Personal emails shown to anyone who typed a JAMB number | Partly hidden for strangers |
| Medium | Browser CSV downloads missed some formula prefixes | One shared CSV rule |
| Medium | A nearly valid id gave a 500 | Checked at the route: 400 |
| Low | Made-up page-crash reports could use up the alert emails | Page errors get 5 of the 20 a day |

Known limits that remain: the head-turn direction is known to the phone just before capture; the phone rule relies on the browser's device token; the page CSP still allows inline scripts (Next.js bootstrap); a 6-character course code is about 30 bits (rate-limited).

## Backups (ADR 035)

- **What is copied:** the whole database, including registered faces and kept check-in photos, every night.
- **Who can read a copy:** only a holder of the private age key. Keys are made with `pnpm backup:keygen` on a maintainer's computer. GitHub holds only public keys and ciphertext.
- **Where copies are kept:** releases of a separate **private** repository. The job refuses a public one. Its token is fine-grained, with Contents on that repository only.
- **What the job's login can do:** read only (`lasuatos_backup`, checked by the script). A leaked `BACKUP_DATABASE_URL` cannot change or delete data.
- **The unencrypted dump:** exists only inside the run, and is deleted before upload. On a maintainer's computer it exists only during a restore, which the guide says to delete afterwards.
- **How long copies live:** 8 weeks at most, also while backups fail. Deleted data leaves backups within 8 weeks, as the privacy notice states. A restore brings back withdrawals made after the copy's time, so the restore guide re-applies them.
- **Reports to the app:** authenticated by GitHub's OIDC token (signature, issuer, audience = the app's origin, repository, workflow file on `main`, event, run). No shared secret exists to leak. Report text is scrubbed of addresses and secrets like other alerts.
- **Lost keys:** losing every private key makes every backup unreadable, so two offline copies are required.

## Location privacy rules

Location is read only on the check-in page of a session with a mapped venue (from the moment it opens, so GPS has time to settle) and only the reading used for the check-in is sent; there is no background tracking. The walking guide's "How far am I?" is worked out on the phone and sends nothing. The session taker sees the outcome, distance and accuracy, not the student's coordinates; only institution administrators see where phones were at check-in, rounded to about a metre, for checking a venue's boundary (`GET /api/v1/admin/venues/{venueId}/evidence`). When evidence is poor the student can try again or be added by hand. Retention of location evidence still needs a decision with LASU.

GPS is a proximity signal, not proof of being inside a classroom. Poor accuracy, stale readings, obstruction, device settings and spoofing can all affect results. A mismatch is a review signal, not automatic proof of misconduct.

## Reporting a security concern

This repository has no public security contact configured yet. Report concerns through the app's contact page (`/contact`) without including secrets or personal data. The institution should designate a private reporting address, an incident owner and a response procedure. Do not place credentials, personal information or student records in a public issue.
